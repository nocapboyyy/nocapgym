# План оптимизации запуска и истории NocapGym

**Цель** — пользователь с годом тренировок так же быстро получает доступ к своему плану или активной тренировке, как пользователь с короткой историей. История, календарь и прогресс сохраняют доступ ко всем прежним данным. Работу выполнить на текущем стеке Fastify, TypeScript, Prisma, SQLite, React и Vite.

## Отправная точка и критерий результата

Сейчас после `GET /api/me` функция `fetchWorkoutData` в `apps/web/src/App.tsx` ожидает общий `Promise.all`. Среди зависимостей первого экрана — полный `GET /api/history` с упражнениями и подходами. При завершении и удалении тренировки клиент повторяет этот запрос.

Локальная исходная точка — Node.js 22, временная SQLite, один пользователь, 6 упражнений по 4 подхода на тренировку. Для 12 / 52 / 156 тренировок текущий ответ содержит 90 / 392 / 1 175 КБ JSON. Через Fastify inject после прогрева медианы составили 5,9 / 17,9 / 49,9 мс. Экспериментальная выборка 20 карточек для той же базы заняла 9,4 КБ. Это ориентиры для повторения эксперимента. Базовый p95 на VPS и время до доступного экрана в Telegram предстоит измерить.

**Приёмка первого релиза:** в двух аккаунтах с одинаковыми планами, активной сессией и тренировками за видимую неделю добавление старых тренировок с 12 до 156 не меняет состав стартовых запросов и объём данных первого экрана, кроме различий в идентификаторах. Первый запрос списка истории возвращает до 20 карточек. Старое упражнение доступно в фильтре прогресса до загрузки второй страницы. Завершение и удаление обходятся без повторной загрузки всей истории.

## 1. Добавить API для карточек, календаря и фильтра прогресса

**Начать здесь.** Реализовать маршруты чтения в `apps/api/src/routes/` и зарегистрировать их в `server.ts`, если они вынесены в отдельный файл. Существующие `GET /api/history`, запрос точек прогресса по ID и формат резервной копии продолжают обслуживать старые WebView.

| Новый GET-маршрут | Ответ и правила выборки |
|---|---|
| `/api/history/page?limit=20&cursor=…` | `{ items, nextCursor }`. Поля карточки: `id, startedAt, completedAt, planTitle, exerciseNames: string[]`. Названия упражнений идут в порядке тренировки, с повторами. Заголовок — первый непустой вариант из исторического снимка, текущего имени связанного плана и «План не найден». Только завершённые тренировки текущего пользователя. |
| `/api/history/calendar?from=…&to=…` | `{ items: [{ id, startedAt }] }` за полуоткрытый интервал `[from, to)` по **началу** завершённой тренировки. Клиент передаёт две абсолютные ISO-даты с часовым смещением или Z, вычисленные из локальных границ видимой сетки. Клиент превращает их в отметки по местному дню. |
| `/api/progress/exercises` | `{ items: [{ id, name }] }` по всей истории пользователя. Включать каждое упражнение один раз, если есть завершённая тренировка и хотя бы один выполненный рабочий подход с заполненными фактическими весом и повторами. Скрытые упражнения сохраняются. Оставить текущую сортировку названий через `localeCompare(..., 'ru')` на клиенте. |

Сортировка стабильна по `completedAt DESC, id DESC`. Непрозрачный курсор кодирует значения последней выданной пары. Сравнивать значения, чтобы следующая страница открывалась и после удаления граничной записи. Учесть записи из старого импорта с `status=completed` и `completedAt=null`: выводить после датированных, внутри группы сортировать по ID. Некорректные параметры возвращают штатный 400.
- [x] Для календаря валидировать обе даты и порядок границ. Для ограничения запроса достаточно 43 суток, включая запас на переход часов в шестинедельной сетке. Для фильтра прогресса начать с выборки `Exercise` с вложенным условием существования подходящих записей. Ограничение `userId` брать из `request.user` во всех трёх маршрутах.
- [x] Проверить в SQLite планы запросов истории и календаря на синтетических данных. Текущий индекс истории заканчивается на `completedAt`, а календарь фильтрует по `startedAt`. Отдельный индекс добавлять миграцией, если `EXPLAIN QUERY PLAN` и замер покажут пользу.
- [x] Интеграционные тесты: два пользователя, пустая история, одинаковые даты завершения, две страницы без повторов, удаление записи курсора, старый импорт с пустой датой, переименованный и удалённый план, скрытое упражнение. Для календаря — обе границы интервала и тренировка через полночь. Для прогресса — упражнение только на старой странице, разминка, пропущенный подход и нулевой фактический вес.

**Готово**, когда новый API проходит эти тесты, первая страница содержит максимум запрошенное число карточек, а в ответах карточек и календаря отсутствуют массивы подходов.
